# Databricks vs AWS: component map

Generated from the 3D lab. Each row is one box in the diagram; the boxes sit in the same place on both stacks.

| step | Databricks | AWS | Key points |
|---|---|---|---|
| 1. Sources | **Store POS terminals** (customer system)<br>Every basket becomes an event: store, SKU, quantity, price, time. Thousands of stores, with peaks on promotion days. | **Store POS terminals** (customer system)<br>Every basket becomes an event: store, SKU, quantity, price, time. Thousands of stores, with peaks on promotion days. | Both sides start in the same place: POS is a customer system and belongs to neither platform. First ask about peak TPS, acceptable latency, and how stores resend data after a network outage. |
| 1. Sources | **Promo calendar, weather, holidays** (customer system)<br>Promotion plans, price changes, weather and public holidays, delivered as files or APIs. Promotions are usually the strongest demand driver. | **Promo calendar, weather, holidays** (customer system)<br>Promotion plans, price changes, weather and public holidays, delivered as files or APIs. Promotions are usually the strongest demand driver. | Promotions, price, weather and holidays usually improve accuracy more than switching algorithms, so include them first in the design. |
| 1. Sources | **ERP and WMS (SAP, Oracle)** (customer system)<br>System of record for stock on hand per warehouse and store, open purchase orders, inbound shipments and the product master. | **ERP and WMS (SAP, Oracle)** (customer system)<br>System of record for stock on hand per warehouse and store, open purchase orders, inbound shipments and the product master. | The ERP is the system of record: both solutions read it in through CDC and write suggested orders back. Neither replaces the ERP. |
| 2. Ingest | **Apache Kafka** (open source / third party)<br>Durable event buffer between tills and the platform, with replay after a bug fix. Databricks reads it with the Structured Streaming Kafka source inside a Lakeflow pipeline. The Kafka cluster itself can be Confluent or Amazon MSK.<br>[doc](https://docs.databricks.com/aws/en/connect/streaming/kafka/) | **Amazon MSK** (AWS)<br>Managed Apache Kafka. Kinesis Data Streams is the AWS-native alternative when you do not need Kafka APIs.<br>[doc](https://docs.aws.amazon.com/msk/latest/developerguide/what-is-msk.html) | Kafka is outside the platform on both sides. Databricks on AWS reading MSK directly is common: this is a point of coexistence, not competition. |
| 2. Ingest | **Auto Loader** (Databricks)<br>Processes new files as they land in S3 or Unity Catalog volumes (the cloudFiles source), with schema inference and evolution and exactly-once writes to Delta. Databricks recommends it inside Lakeflow pipelines.<br>[doc](https://docs.databricks.com/aws/en/ingestion/cloud-object-storage/auto-loader/) | **S3 landing + AWS Glue jobs** (AWS)<br>Files land in an S3 prefix. Glue jobs pick up only new files using job bookmarks, on a schedule or triggered by S3 events through EventBridge.<br>[doc](https://docs.aws.amazon.com/glue/latest/dg/what-is-glue.html) | Auto Loader only ingests 'files'; it does not read Kafka. AWS has no one-to-one service; it is usually assembled from S3 events + Glue bookmarks. |
| 2. Ingest | **Lakeflow Connect** (Databricks)<br>Managed ingestion from databases and SaaS apps into streaming tables, with change data capture. Part of Lakeflow, next to pipelines and jobs. For an occasional read-only query on the source without copying it, Lakehouse Federation queries the database in place instead.<br>[doc](https://docs.databricks.com/aws/en/ingestion/overview) | **Zero-ETL or AWS DMS** (AWS)<br>Zero-ETL integrations bring operational databases and apps such as SAP and Salesforce into the lakehouse in near real time. AWS DMS covers other change-data-capture sources.<br>[doc](https://docs.aws.amazon.com/glue/latest/dg/zero-etl-using.html) | Zero-ETL maps to Lakeflow Connect (CDC), not to Auto Loader. Which ERP connectors are supported depends on the customer's versions, so check rather than promise on the spot. Another option is Lakehouse Federation: it queries the source database in place, read-only and without copying, which suits the occasional query. For high volume, low latency or keeping history (SCD type 2), the docs recommend Lakeflow Connect. |
| 3. Raw (bronze) | **Structured Streaming, real-time mode** (Databricks)<br>Computes rolling features, such as units sold in the last 15 minutes per store and SKU, and writes them directly to the Online Feature Store through Stream Feature Views.<br>[doc](https://docs.databricks.com/aws/en/structured-streaming/real-time/concepts) | **Managed Service for Apache Flink** (AWS)<br>Flink applications compute windowed aggregates on MSK or Kinesis and write them to the SageMaker Feature Store online store.<br>[doc](https://docs.aws.amazon.com/managed-flink/latest/java/what-is.html) | Databricks uses one Spark engine for batch and streaming; on AWS it is common to use Spark (Glue/EMR) for batch and Flink for streaming, which means two skill sets and two sets of operations. |
| 3. Raw (bronze) | **Bronze streaming tables** (Databricks)<br>Raw Delta tables written by the Lakeflow pipeline. Nothing is cleaned here, so silver and gold can always be rebuilt.<br>[doc](https://docs.databricks.com/aws/en/ldp/) | **Raw Iceberg tables in S3 Tables** (AWS)<br>Raw events land in Apache Iceberg tables in an S3 table bucket, written by Amazon Data Firehose or Glue streaming jobs.<br>[doc](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables.html) | Both sides use open table formats (Delta / Iceberg); AWS is not closed either. |
| 4. Clean (silver) | **Silver: Lakeflow Spark Declarative Pipelines** (Databricks)<br>Declarative SQL or Python: dedupe, handle late events and store time zones, keep product master history. Expectations drop or quarantine bad rows and count them.<br>[doc](https://docs.databricks.com/aws/en/ldp/) | **AWS Glue ETL or EMR Serverless** (AWS)<br>Spark jobs authored in SageMaker Unified Studio notebooks or Visual ETL, running on Glue or EMR Serverless. Data quality rules check each run.<br>[doc](https://docs.aws.amazon.com/glue/latest/dg/what-is-glue.html) | DLT has been renamed Lakeflow pipelines (Spark Declarative Pipelines). This layer is the core of Databricks data engineering and is worth the most practice time. |
| 5. Curated (gold) | **Databricks SQL warehouse** (Databricks)<br>Serverless compute for SQL on the gold tables. Photon, the native vectorized engine, is the default on every SQL warehouse. AI/BI dashboards and Genie run on it, and tools such as Power BI, Tableau or Amazon Quick connect to it, with Unity Catalog permissions applied to every query.<br>[doc](https://docs.databricks.com/aws/en/compute/sql-warehouse/) | **Amazon Athena or Redshift Serverless** (AWS)<br>Athena runs serverless SQL directly on the Iceberg tables. Redshift Serverless is the warehouse option for heavier, high-concurrency dashboards. Quick Sight and other BI tools connect to either, with Lake Formation permissions applied.<br>[doc](https://docs.aws.amazon.com/athena/latest/ug/what-is.html) | In the reference architecture, serving is not only models: BI needs a SQL engine too. On Databricks that is a SQL warehouse (Photon by default); on AWS, Athena or Redshift. The pricing model and the expected concurrency are the design questions to ask first. |
| 5. Curated (gold) | **Gold materialized views** (Databricks)<br>Business-level tables: daily sales per store and SKU, stock position per warehouse and SKU. One source for dashboards and models, so the numbers agree.<br>[doc](https://docs.databricks.com/aws/en/ldp/) | **Curated Iceberg tables** (AWS)<br>Curated tables in the SageMaker lakehouse architecture, registered in the Glue Data Catalog and queried by Athena or Redshift.<br>[doc](https://docs.aws.amazon.com/sagemaker-unified-studio/latest/userguide/lakehouse.html) | One gold layer feeds both BI and ML, so the numbers on both sides stay consistent. |
| 5. Curated (gold) | **OpenSharing (formerly Delta Sharing)** (Databricks)<br>Share live gold tables or views, such as daily sell-through per SKU, with suppliers. Recipients on Databricks see them in their own Unity Catalog; recipients without Databricks read them through the open protocol. No extract files and no copies to keep in sync.<br>[doc](https://docs.databricks.com/aws/en/opensharing/) | **Lake Formation cross-account sharing** (AWS)<br>Grant Lake Formation permissions on a table or a data cells filter to another AWS account; AWS RAM delivers the share. The supplier needs an AWS account and creates a resource link to query it with Athena. Suppliers outside AWS need another route, such as exports.<br>[doc](https://docs.aws.amazon.com/lake-formation/latest/dg/cross-account-permissions.html) | The Delta Sharing in the reference architecture is now called OpenSharing. A common retail use: share sell-through and stock with suppliers (vendor-managed inventory, collaborative replenishment). The key difference is whether the other side must be on the same platform: an OpenSharing recipient does not need Databricks, while Lake Formation sharing needs the supplier to have an AWS account. |
| 6. Features | **Online Feature Store** (Databricks)<br>Powered by Lakebase. Model Serving looks features up automatically, so the store app only sends store and SKU.<br>[doc](https://docs.databricks.com/aws/en/machine-learning/feature-store/online-feature-store) | **SageMaker Feature Store, online** (AWS)<br>The online store of the same feature group serves the latest values with low latency.<br>[doc](https://docs.aws.amazon.com/sagemaker/latest/dg/feature-store.html) | Official docs: the Online Feature Store is powered by Lakebase. The old Online Tables are no longer the recommended approach. |
| 6. Features | **Feature Store in Unity Catalog** (Databricks)<br>Feature Views (Public Preview) or feature tables governed in Unity Catalog. Point-in-time joins stop training from seeing the future, and models record which features they used.<br>[doc](https://docs.databricks.com/aws/en/machine-learning/feature-store/) | **SageMaker Feature Store, offline** (AWS)<br>Feature groups with an offline store in S3 for training. AWS docs point you to SageMaker Studio, not Unified Studio, when you need Feature Store.<br>[doc](https://docs.aws.amazon.com/sagemaker/latest/dg/feature-store.html) | The AWS documentation says it directly: use SageMaker Studio when you need Feature Store or Canvas, so the data and ML experiences are still separate. On Databricks, features are UC objects. |
| 7. Train and register | **MLflow 3, managed** (Databricks)<br>Databricks-managed MLflow tracks every run, parameter and metric. MLflow 3 adds Logged Models and deployment jobs governed by Unity Catalog.<br>[doc](https://docs.databricks.com/aws/en/mlflow/) | **Managed MLflow on SageMaker AI** (AWS)<br>MLflow Apps (MLflow 3.x) or tracking servers. Models can auto-register into SageMaker Model Registry.<br>[doc](https://docs.aws.amazon.com/sagemaker/latest/dg/mlflow.html) | Both sides use MLflow. Databricks created MLflow and integrates it natively with UC. SageMaker Experiments remains only in Studio Classic and is no longer the main option. |
| 7. Train and register | **Many-models training** (Databricks)<br>groupBy(store, sku).applyInPandas fans out thousands of small LightGBM or Prophet models in parallel on Spark, each run logged to MLflow.<br>[doc](https://docs.databricks.com/aws/en/pandas/pandas-function-apis) | **SageMaker AI training jobs** (AWS)<br>Custom per-series training fanned out across training or processing jobs. For low-code, SageMaker Canvas forecasts per item ID. Amazon Forecast is no longer available to new customers.<br>[doc](https://docs.aws.amazon.com/sagemaker/latest/dg/train-model.html) | Tens of thousands of store×SKU time series = the many-models pattern, not Mosaic AI Training (that is LLM fine-tuning). On the AWS side: Amazon Forecast is closed to new customers, and the official advice is to move to SageMaker Canvas. |
| 7. Train and register | **Models in Unity Catalog** (Databricks)<br>Model versions live in Unity Catalog with aliases and lineage back to features and tables. Promotion is an alias swap, so rollback is one line.<br>[doc](https://docs.databricks.com/aws/en/machine-learning/manage-model-lifecycle/) | **SageMaker Model Registry** (AWS)<br>Model package groups with versions and an approval status that pipelines check before deploying.<br>[doc](https://docs.aws.amazon.com/sagemaker/latest/dg/model-registry.html) | Databricks: models, tables and features share one permission model. AWS: Model Registry permissions go through IAM, data permissions through Lake Formation. |
| 8. Serve | **Model Serving endpoint** (Databricks)<br>Serverless REST endpoint for intraday re-forecasts. It scales with demand, looks up online features itself and captures requests and responses for monitoring.<br>[doc](https://docs.databricks.com/aws/en/machine-learning/model-serving/) | **SageMaker AI real-time endpoint** (AWS)<br>Real-time endpoint with autoscaling, usually fronted by API Gateway and Lambda for the store app.<br>[doc](https://docs.aws.amazon.com/sagemaker/latest/dg/realtime-endpoints.html) | Model Serving supports both real-time and batch inference (official documentation). Design latency targets around the SLA, and do not quote numbers without a source. |
| 8. Serve | **Data quality monitoring** (Databricks)<br>Anomaly detection watches freshness and completeness of every table. Data profiling (formerly Lakehouse Monitoring) tracks drift on inference tables. Alerts trigger retraining.<br>[doc](https://docs.databricks.com/aws/en/data-governance/unity-catalog/data-quality-monitoring/) | **Data Capture + MLflow Apps + Evidently** (AWS)<br>SageMaker Model Monitor is no longer open to new customers. AWS's documented replacement: Data Capture to S3, open-source monitoring solutions built on SageMaker AI MLflow Apps and Evidently AI, CloudWatch alarms and Quick Sight dashboards.<br>[doc](https://docs.aws.amazon.com/sagemaker/latest/dg/model-monitor-availability-change.html) | Most forecasting incidents are late or missing data, not a broken model, so monitor the data first, then the model. On the AWS side, note that SageMaker Model Monitor is closed to new customers; the replacement is something you deploy yourself (MLflow Apps + Evidently + CloudWatch). |
| 8. Serve | **Batch inference job** (Databricks)<br>A Lakeflow Jobs task scores every warehouse and SKU 30 days ahead each night and writes a gold forecast table.<br>[doc](https://docs.databricks.com/aws/en/jobs/) | **SageMaker Batch Transform** (AWS)<br>Nightly batch transform triggered by SageMaker Pipelines or Step Functions. Results land in S3 and load into Redshift.<br>[doc](https://docs.aws.amazon.com/sagemaker/latest/dg/batch-transform.html) | The forecast is a “table”: ERP, BI and the agent read the same numbers. |
| 9. Use | **Store sales forecast** (business outcome)<br>Store managers see today's top-ups and staffing in a Databricks App that calls the endpoint.<br>[doc](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/) | **Store sales forecast** (business outcome)<br>A store app calls the endpoint through API Gateway and Lambda.<br>[doc](https://docs.aws.amazon.com/apigateway/latest/developerguide/welcome.html) | Success is measured by stockout rate, waste rate and labor cost, not just model accuracy. |
| 9. Use | **Genie + Agent Bricks** (Databricks)<br>Planners ask why a forecast moved and Genie answers over governed data. A replenishment agent built with Agent Bricks calls the forecast endpoint and drafts orders for approval. Models and tools go through Unity Gateway.<br>[doc](https://docs.databricks.com/aws/en/agents/) | **Amazon Quick + Bedrock AgentCore** (AWS)<br>Quick answers questions and hosts dashboards. A replenishment agent on AgentCore Runtime uses Gateway tools to call the endpoint, with Policy and Evaluations around it.<br>[doc](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html) | Key points: human-in-the-loop, tool governance (Unity Gateway vs AgentCore Gateway + Policy), evaluation (MLflow 3 vs AgentCore Evaluations). Unity Gateway can use the customer's existing Amazon Bedrock capacity, a point of coexistence. |
| 9. Use | **Warehouse inventory forecast** (business outcome)<br>Suggested orders sync back to the ERP for planners to approve. AI/BI dashboards show coverage and stock-out risk.<br>[doc](https://docs.databricks.com/aws/en/dashboards/) | **Warehouse inventory forecast** (business outcome)<br>Suggested orders go back to the ERP. Amazon Quick Sight dashboards for planners.<br>[doc](https://docs.aws.amazon.com/quick/latest/userguide/what-is.html) | The ERP is still the ordering system; forecasts only produce 'suggestions', which planners approve. |

## Layers under and over every step

| layer | Databricks | AWS | Key points |
|---|---|---|---|
| Where people work and how jobs run | **Databricks workspace + Lakeflow Jobs**<br>Notebooks, SQL editor, pipelines and dashboards in one workspace. Lakeflow Jobs orchestrates ingest, train, score and refresh as one DAG.<br>[doc](https://docs.databricks.com/aws/en/jobs/) | **SageMaker Unified Studio**<br>One IDE that brings together Glue, EMR, Athena, Redshift, MWAA, Bedrock and SageMaker AI.<br>[doc](https://docs.aws.amazon.com/sagemaker-unified-studio/latest/userguide/what-is-sagemaker-unified-studio.html)<br><br>**SageMaker AI Studio**<br>AWS docs: use SageMaker Studio when you need Feature Store or Canvas.<br>[doc](https://docs.aws.amazon.com/next-generation-sagemaker/latest/userguide/what-is-sagemaker.html)<br><br>**Pipelines / Step Functions**<br>SageMaker Pipelines or Step Functions orchestrate training, approval and batch scoring.<br>[doc](https://docs.aws.amazon.com/sagemaker/latest/dg/pipelines.html) | Databricks: one workspace. AWS: Unified Studio covers data and analytics, while Feature Store / Canvas are still in SageMaker AI Studio (stated in the official documentation). |
| Governance | **Unity Catalog**<br>One permission model and lineage graph for tables, volumes, features, models, functions and serving endpoints, extended to agents and MCP tools through Unity Gateway. Row filters, column masks and audit. Catalog federation brings tables still registered in AWS Glue or a Hive metastore under the same permissions.<br>[doc](https://docs.databricks.com/aws/en/data-governance/unity-catalog/) | **SageMaker Catalog**<br>Discovery, publish and subscribe, data quality and lineage across data and AI assets.<br>[doc](https://docs.aws.amazon.com/sagemaker-unified-studio/latest/userguide/working-with-business-catalog.html)<br><br>**Lake Formation + Glue Data Catalog**<br>Fine-grained table, column and row permissions on S3 data, plus technical metadata.<br>[doc](https://docs.aws.amazon.com/lake-formation/latest/dg/what-is-lake-formation.html)<br><br>**IAM**<br>Who can call Feature Store, training, Model Registry and endpoints.<br>[doc](https://docs.aws.amazon.com/IAM/latest/UserGuide/introduction.html) | This is the most important difference: on Databricks, one set of permissions and one lineage graph run from the POS table to the endpoint; AWS governance is three layers that have to be kept aligned. Be fair and stick to facts. If the customer already has a Glue Data Catalog, catalog federation can bring it under Unity Catalog first, with tables migrated step by step instead of all at once. |
| Storage | **Your Amazon S3, open formats**<br>Delta Lake tables in the customer's own S3 buckets. Compute, serverless or classic, is separate from storage. | **Amazon S3 + S3 Tables**<br>General purpose buckets plus table buckets that store Apache Iceberg tables with automatic compaction.<br>[doc](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables.html) | On both sides the data sits in the customer's own S3 in open formats. Databricks on AWS does not move the data away; it adds a platform on top of the same S3. |
| Foundation: identity, security, cost, CI/CD | **Databricks account: identity, cost, CI/CD**<br>SSO and SCIM provisioning from your identity provider, such as Okta or Microsoft Entra ID. System tables for billing, audit and lineage, queried with SQL. Declarative Automation Bundles (formerly Databricks Asset Bundles) deploy jobs, pipelines and endpoints from Git through GitHub Actions or another CI system.<br>[doc](https://docs.databricks.com/aws/en/dev-tools/bundles/)<br><br>**Your AWS account: keys, network, audit**<br>Customer-managed keys in AWS KMS, a customer-managed VPC with private connectivity, CloudTrail for the S3 side and CloudWatch for the infrastructure. Databricks on AWS runs on this foundation, so this part is shared with the AWS stack.<br>[doc](https://docs.databricks.com/aws/en/security/) | **IAM Identity Center + KMS + CloudTrail**<br>Workforce sign-in and user sync from your identity provider, encryption keys in KMS, secrets in Secrets Manager, and a CloudTrail record of every API call.<br>[doc](https://docs.aws.amazon.com/singlesignon/latest/userguide/what-is.html)<br><br>**CloudWatch + Cost Explorer + CI/CD**<br>CloudWatch metrics, logs and alarms. Cost Explorer with cost allocation tags. CloudFormation or CDK deployed from GitHub Actions or CodePipeline.<br>[doc](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-what-is.html) | This matches the bottom band of the official reference architecture: identity, security, monitoring, cost and DevOps. Most of this layer is the same on both stacks: it lives in the customer's own AWS account (KMS, VPC, CloudTrail) and connects to the same identity provider. What Databricks adds is system tables inside the platform (billing, audit and lineage, all queryable with SQL) and Declarative Automation Bundles. On AWS, a consistent tagging scheme is what lets you add up one pipeline's cost across services. |
