# Databricks × AWS full-stack self-study

**Live site: [timwukp.github.io/databrick-sagamker-full-stack-self-learning](https://timwukp.github.io/databrick-sagamker-full-stack-self-learning/)** — open it in any browser, nothing to install.

**English edition: [timwukp.github.io/databrick-sagamker-full-stack-self-learning/en/](https://timwukp.github.io/databrick-sagamker-full-stack-self-learning/en/)** — the same site, fully in English. Each page links to the other language.

One retail forecasting use case, built end to end twice: on Databricks and on AWS (SageMaker and related services). From the raw POS events in thousands of stores to a nightly warehouse inventory forecast and an intraday store sales forecast, with every step shown as a 3D interactive diagram, synthetic sample data before and after the step, the schema, and links to the official documentation.

## What you will learn

Work through the site once and you should be able to:

- **walk the whole pipeline** — sources → ingest → bronze → silver → gold → features → train and register → serve → use — and name the Databricks and the AWS component at each step;
- **read the data at every step** — what the raw POS JSON, the Kafka record, the bronze row, the silver line and the gold aggregate actually look like, and which columns were added, retyped or removed;
- **see the parts around the pipeline** — a SQL engine for BI (SQL warehouse vs Athena or Redshift), sharing data with suppliers (OpenSharing vs Lake Formation cross-account sharing), federation for systems you do not ingest, and the foundation of identity, keys, audit, cost and CI/CD;
- **spot the platform differences that matter** — Delta vs Iceberg types, Auto Loader's default `STRING` inference and `_rescued_data`, SCD type 2 vs DMS `Op` columns, Feature Store record identifiers, automatic feature lookup vs `GetRecord`, one Unity Catalog vs three governance layers;
- **avoid the common mistakes** — outdated names (DLT, Lakehouse Monitoring, Delta Sharing — now OpenSharing, SageMaker Experiments), wrong data flows (Kafka into Auto Loader) and retired services (Amazon Forecast and SageMaker Model Monitor are closed to new customers);
- **run part of it yourself** on Databricks Free Edition with the same five POS events.

## Change something

The Chinese lab page holds the data. If you add or change Chinese text, add its English to `i18n/en.json`. After editing:

```sh
node scripts/export_from_lab.mjs   # data/ and docs/data-walkthrough.md, docs/databricks-vs-aws-mapping.md
python3 scripts/build_portal.py    # index.html
python3 scripts/build_en.py        # en/ pages + docs/en (fails if any Chinese text has no translation)
node scripts/export_from_lab.mjs --lang en   # docs/en/data-walkthrough.md, docs/en/databricks-vs-aws-mapping.md
python3 verify.py                  # must print OK
```

`verify.py` uses the standard library only. It checks structure, that no page loads an external resource, that every relative link and lab deep link resolves, that every CSV matches its schema, that the synthetic numbers reconcile across steps (line amounts, gold revenue, the 1,104-unit order, the stream windows, the agent trace), neutral wording, no credentials or private paths, and that the JavaScript, notebook and publish script parse. It prints the number of checks it ran.

## Hands-on lab

Import [`labs/01_retail_medallion.py`](labs/01_retail_medallion.py) into Databricks Free Edition (*Workspace → Import*) and run it top to bottom. It writes the five POS events into a Unity Catalog volume, ingests them with Auto Loader into bronze, builds silver and gold, and asserts that your tables match the lab. Everything lives in `workspace.retail_lab`; the last cell drops it.

The notebook was written against the October 2026 documentation and syntax-checked, but has not yet been executed end to end.

## How it publishes

GitHub Pages serves this repository from branch `main`, path `/`, so `index.html` stays at the root. `.nojekyll` turns off Jekyll so files are served exactly as committed.

Publishing uses the GitHub Git Data API instead of `git push` (blobs → tree → commit → ref), never with `force`:

```sh
gh auth login                 # once; token needs the repo scope
bash scripts/publish.sh       # first run: creates or bootstraps the repo, publishes main, enables Pages
bash scripts/publish.sh       # later runs: opens a pull request
bash scripts/publish.sh --direct   # later runs: fast-forward main instead
bash scripts/publish.sh --dry-run  # list the files, change nothing
```

The script runs `verify.py` and a secret scan first, uploads one blob per file (tab-separated list, so paths with spaces work), bootstraps an empty repository through the Contents API (the Git Data API returns 409 on an empty repo), signs the commit with the account's noreply address, and enables Pages on `main /`. On later runs it also deletes files that exist on `main` but no longer exist locally (for example when steps are renumbered), so the repository mirrors this folder; the pull request shows them as deletions.

## About the data

Synthetic and internally consistent: three stores (Singapore, Kuala Lumpur, Bangkok), two warehouses, three SKUs, one business day (2026-10-09) with a promotion. The raw events deliberately contain a duplicate, a late arrival, a new field, a bad scan and nested baskets so each step has something to fix. Values are not benchmarks; column names, types and system fields follow the official documentation. See [`docs/sources.md`](docs/sources.md).
